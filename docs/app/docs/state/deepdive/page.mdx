# Introduction to State

State is the core of your Loomi application. Unlike traditional frameworks where state management feels like an afterthought, Loomi builds state awareness directly into its operational design.

What makes Loomi's approach different? In most Python applications, you pass state through chains of functions, maintain context manually, and fight complexity as your application grows.

```python
def process_order(order_data, customer, inventory):
    # Update inventory state
    # Update customer state
    # Create shipping label
    # Update order state
    # ...and so on
```

Loomi flips this model. State becomes an inherent part of your application's operational mesh, not a separate concern you need to manage.

### State Philosophy

Three key principles define Loomi's approach to state:

1. **State as the source of truth** - Your application's state represents the complete picture of what your app knows at any point.

2. **Isolated yet accessible** - Each app's state lives under its own prefix, preventing collisions while still allowing access to other sections when needed.

3. **State binding** - Operations connect directly to the state they need, making state access natural and contextual.

This foundation creates what we call the Lmesh™—a pattern of interconnected, state-aware operations that form the foundation of Loomi applications.

### Why This Matters

When state binds to operations, several powerful things happen:

- Your code focuses on what it does, not how state moves around
- Composition becomes natural—apps can be composed from smaller pieces
- Reliability increases as state-related bugs become less common
- Testing improves because operations have clear state boundaries

By weaving state awareness into your application's foundation, complex architectural challenges become simple patterns.

## Accessing App State

Every Loomi app provides access to its state through the `state` property (with `s` as a convenient shorthand):

```python {3,5} /\.state./1 /\.s\./1 showLineNumbers
# These are equivalent
# Full property
user_data = await app.state.dict("users", "profiles").to_python_object()
# Shorthand
user_data = await app.s.dict("users", "profiles").to_python_object()
```

This returns an instance of either `AsyncStateProtocol` or `SyncStateProtocol` depending on your app type. These protocols define a consistent interface for interacting with Loomi's state system.

### State Protocols

The state protocols provide methods to:

- Access dictionary and list nodes within the state tree
- Check existence and type of nodes
- Manage transactions
- Subscribe to state changes

What matters most is that they give you a clean, Pythonic interface for working with nested state.

### Sync vs Async

Loomi supports both synchronous and asynchronous state patterns with nearly identical interfaces:

```python {2,5} showLineNumbers
# Asynchronous
await async_app.s.dict("config").set("feature_flags", "dark_mode", value=True)

# Synchronous
sync_app.s.dict("config").set("feature_flags", "dark_mode", value=True)
```

We'll focus primarily on the async interface in our examples, but the sync version works almost identically—just without the `await` keywords.

## Working with State

Loomi's state system feels like using Python's built-in types. This makes working with state easy and familiar, even when your data is persisted.

### Path-Based Access

All state access uses paths to navigate the state tree:

```python
# Access user data with path segments
user_prefs = await app.s.dict("users", str(user_id), "preferences")

# Each segment navigates deeper into the tree
system_settings = await app.s.dict("system", "settings", "notifications")
```

Think of paths as stepping stones into your data. Each path segment (like `"users"` or `user_id`) takes you one level deeper.

### Dict Interface

The TreeDict interface works like Python dictionaries:

```python
# Get a dictionary node
config = await app.s.dict("config")

# Set a value
await config.set("version", value="1.2.3")

# Get a value (with default if it doesn't exist)
app_name = await config.get("app_name", default="MyApp")

# Check if a key exists
has_logging = await config.contains("logging")

# Delete a key
await config.delete("old_setting")
```

Common dict methods:

| Method | Description |
|--------|-------------|
| `get(key, default=None)` | Get a value with optional default |
| `set(key, value=value)` | Set a key to a value |
| `delete(key)` | Remove a key and its value |
| `contains(key)` | Check if a key exists |
| `keys()` | Get all keys in the dictionary |
| `values()` | Get all values in the dictionary |
| `items()` | Get all key-value pairs |
| `update(dict)` | Update with key-values from a dict |
| `clear()` | Remove all items |
| `to_dict()` | Convert underlying tree to a Python dict |

[API Reference: TreeDict Interface](/api/state/tree-dict)

### List Interface

The TreeList interface works like Python lists:

```python
# Get a list node
tasks = await app.s.list("tasks")

# Add items
await tasks.append({"title": "New task", "done": False})

# Get an item by index
first_task = await tasks.get(0)

# Update an item
await tasks.set(0, {"title": "Updated task", "done": True})

# Get list length
count = await tasks.length()

# Remove an item
await tasks.delete(0)
```

Common TreeList Methods

| Method | Description |
|--------|-------------|
| `get(index)` | Get item at index |
| `set(index, value)` | Set item at index |
| `append(value)` | Add item to the end |
| `extend(list)` | Add multiple items to the end |
| `insert(index, value)` | Insert item at index |
| `delete(index)` | Remove item at index |
| `length()` | Get number of items |
| `clear()` | Remove all items |
| `to_list()` | Convertunderlying tree to a Python list |

[API Reference: TreeList Interface](/api/state/tree-list)

### Python Object Conversion

You can convert between state objects and Python objects:

```python
# Get state as Python objects
config_dict = await app.s.dict("config").to_python_object()
tasks_list = await app.s.list("tasks").to_list()

# Store Python objects in state
await app.s.dict("config").store({
    "version": "1.2.3",
    "features": ["search", "export"],
    "limits": {
        "users": 10,
        "storage": "5GB"
    }
})

# Store a list
await app.s.list("recent").store(["item1", "item2", "item3"])
```

This makes it easy to work with complex data structures.

### Nested Access

You can access deeply nested data:

```python
# Access nested data with path segments
user_theme = await app.s.dict("users", user_id, "preferences", "display").get("theme")

# Or navigate step by step
user = await app.s.dict("users", user_id)
prefs = await user.dict("preferences")
display = await prefs.dict("display")
theme = await display.get("theme")
```

Both approaches work the same. Choose what feels more readable for your code.

## Transactions

### Basic Transactions

Transactions let you make multiple changes as a single unit. Either all changes succeed, or none do.

```python
async def transfer_funds(self, from_account: str, to_account: str, amount: float):
    async with await self.s.transaction() as txn:
        # Get current balances
        from_balance = await self.s.dict("accounts", from_account, txn=txn).get("balance")
        to_balance = await self.s.dict("accounts", to_account, txn=txn).get("balance")
        
        # Ensure sufficient funds
        if from_balance < amount:
            raise ValueError("Insufficient funds")
            
        # Update both accounts (this happens atomically)
        await self.s.dict("accounts", from_account, txn=txn).set("balance", from_balance - amount)
        await self.s.dict("accounts", to_account, txn=txn).set("balance", to_balance + amount)
    
    # Transaction auto-commits here if no errors occurred
```

If any step fails, all changes roll back. This keeps your data consistent.

### Manual Transaction Control

You can also control transactions manually:

```python
# Start a transaction
txn = await app.s.begin_transaction()

try:
    # Make changes using the transaction
    await app.s.dict("inventory", txn=txn).set(item_id, "count", value=count - 1)
    await app.s.dict("orders", txn=txn).set(order_id, "status", value="processing")
    
    # Commit when ready
    await txn.commit()
except Exception:
    # Roll back on error
    await txn.rollback()
    raise
```

## Reactive Subscriptions

Subscriptions let you react to state changes in real-time.

### Basic Subscriptions

```python
async def setup_notifications(self):
    # Subscribe to user preference changes
    await self.s.subscribe(
        ("users", self.user_id, "preferences"),  # Path to watch
        self.on_preferences_changed,  # Callback function
        depth=1  # Watch all keys one level deep
    )

async def on_preferences_changed(self, key):
    # React to the change
    print(f"Preference changed: {key}")
    # Update UI, sync with server, etc.
```

The callback runs whenever matching state changes.

### Subscription Depth

The `depth` parameter controls which keys trigger the callback:

```python
# depth=0: Only exact path matches
# This only triggers for the exact "config" key
await app.s.subscribe(("config",), callback, depth=0)

# depth=1: Matches one level deeper
# Triggers for "config.server", "config.client", etc.
await app.s.subscribe(("config",), callback, depth=1)

# depth=-1: Matches all nested paths
# Triggers for any path starting with "config"
await app.s.subscribe(("config",), callback, depth=-1)
```

### Cleaning Up Subscriptions

Always remove subscriptions when done:

```python
# Store subscription object
self._subscription = await app.s.subscribe(path, callback)

# Later, unsubscribe
if self._subscription:
    await app.s.unsubscribe(self._subscription)
    self._subscription = None
```

## Transformations and Filtering

Loomi provides powerful tools to transform and filter state in-place.

### Transform Operations

Use `transform` to update a value in place:

```python
# Update a user record
await app.s.dict("users", user_id).transform(
    lambda user: {
        **user,  # Keep existing data
        "last_active": current_time(),  # Update specific fields
        "login_count": user.get("login_count", 0) + 1
    }
)
```

### Map Operations

Use `map` to transform every item in a collection:

```python
# Apply 10% discount to all products
await app.s.dict("products").map(
    lambda product: {
        **product,
        "price": round(product["price"] * 0.9, 2)
    }
)
```

### Filter Operations

Use `filter` to keep only items matching a condition:

```python
# Keep only active users
await app.s.dict("users").filter(
    lambda _key, user: user.get("status") == "active"
)

# Keep only completed tasks in a list
await app.s.list("tasks").filter(
    lambda task: task.get("completed", False) is True
)
```

For dictionaries, the filter function gets both key and value. For lists, it gets just the value.

### Move and Copy Operations

You can move or copy parts of state:

```python
# Copy user to archive
await app.s.dict("users", user_id).copy_to("archived_users", user_id)

# Move user to different collection
await app.s.dict("pending_users", user_id).move_to("active_users", user_id)
```

## State Adapters

Loomi defines interfaces for state, not implementations. This gives you freedom to choose or build storage backends that fit your needs.

LoomiSTD includes several ready-to-use adapters:

### InMemoryState

Perfect when you need a fast, temporary state store:

```python
from loomistd.state import StateSpec
from loomistd.kv_storage.in_memory import InMemoryStorageSpec

app = AsyncApp(
    # ...
    state_spec=StateSpec(
        storage=InMemoryStorageSpec()
    )
)
```

- **Pros**: Fastest
- **Cons**: No persistance, data lost on restart

### LMDBState

A high-performance persistent key-value store:

```python
from loomistd.state import StateSpec
from loomistd.kv_storage.lmdb import LMDBStorageSpec

app = AsyncApp(
    # ...
    state_spec=StateSpec(
        storage=LMDBStorageSpec(
            path="./data/myapp",
            map_size=10 * 1024 * 1024  # 10MB initial size
        )
    )
)
```

- **Pros**: Fast, durable, ACID-compliant
- **Cons**: Requires file system access
- **Best for**: Production apps, local data storage

### FileState

Simple JSON file-based storage:

```python
from loomi import FileState

app = AsyncApp(
    # ...
    state=FileState(
        path="./data/myapp.json",
        pretty=True  # Format JSON for readability
    )
)
```

- **Pros**: Human-readable, easy to inspect
- **Cons**: Slower, not suitable for large data
- **Best for**: Simple apps, configuration storage, development, testing and debugging

### Switching Adapters

Loomi makes it easy to switch adapters as your needs change:

```python
# Development configuration
if config.DEV_MODE:
    state_adapter = InMemoryStateSpec()
# Testing configuration
elif config.TESTING:
    state_adapter = FileStateSpec(path="./test_data.json")
# Production configuration
else:
    state_adapter = LMDBStateSpec(path="/var/data/myapp")

app = AsyncApp(
    # ...
    state_spec=state_adapter_spec
)
```

You can even migrate data between adapters:

```python
async def migrate_state(source_adapter, target_adapter):
    """Copy all state from one adapter to another."""
    # Start a transaction on the target
    async with await target_adapter.transaction() as txn:
        # List all keys from source
        async for key in source_adapter.list_keys((), depth=-1):
            # Get value from source
            value = await source_adapter.get(key)
            # Set value in target
            await target_adapter.set(key, value, txn=txn)
```

## Conclusion

Loomi's state interface transforms how you work with application state. By making state a first-class citizen in your app architecture, you can:

- **Write clearer code** focused on business logic, not state plumbing
- **Build more robust apps** with transactions and proper state boundaries
- **Compose functionality** by connecting state-aware operations
- **Create reactive systems** through state subscriptions
- **Store data your way** with flexible adapter options

The state interface is just one part of Loomi's Lmesh™ approach. Together with operations, services, and apps, it forms a cohesive system for building maintainable Python applications.
