# Introduction to Operations

Operations form the building blocks of all Loomi applications. They're composable, state-bound functions that know how to execute themselves and interact with your application state.

Unlike traditional functions that work with data passed to them as arguments, Loomi operations are aware of their place in your application and can interact directly with state. 
This state-binding is what makes Loomi operations special - they can read from and write to your application state without complex state-passing logic.

```python
# Traditional approach
def process_data(data, config):
    result = data * config['multiplier']
    return result

# Loomi approach
def process_data(context):
    data = context.scope.get('data')
    multiplier = context.scope.get('config', 'multiplier')
    result = data * multiplier
    context.scope.set('result', result)
```

The executor is what actually runs your operations. It provides the operational building blocks (like Function, Sequence, Branch, etc.) and handles all the execution logic, including error handling, state management, and concurrency. 
Think of it as the engine that powers your Loomi app.

In traditional approaches, you'd have separate systems for control flow, state management, and error handling. 
Loomi's operations interface combines these into a single coherent system where operations are inherently aware of state and can use it to make decisions.

## Operations Philosophy

### Composability: Building Complex from Simple

The real power of Loomi operations is that you can take simple operations and compose them into more complex ones. Then, those complex operations can themselves be composed into even more sophisticated applications.

```python
# Simple operations
fetch_data = Function(fetch_user_data)
validate_data = Function(validate_user_info)

# Compose them into a sequence
process_user = Sequence(
    fetch_data,
    validate_data,
    Function(transform_user_data)
)

# Use that sequence in a higher-level flow
user_flow = Branch(
    {
        "new": process_user,
        "existing": Function(update_user)
    },
    condition_path=("user", "status")
)
```

This composability means you don't need to reinvent the wheel for each application. Build once, compose anywhere.

### Consistency: Uniform Patterns Across Operation Types

All operations follow the same basic patterns. They all:
- Take the same initialization arguments (like error_behavior)
- Execute within a context
- Have the same state access patterns
- Handle errors in consistent ways

Once you learn how one operation type works, the others follow naturally.

### Predictability: Consistent Behavior in Similar Situations

When something goes wrong, operations behave in predictable ways. If an error occurs, depending on your configuration, an operation will either:
- Fail and propagate the error upward
- Record the error and continue with the next operation

This predictability makes debugging and reasoning about your application much easier. No more guessing what happens when things go sideways.

### Explicitness: Clear Intent from Interfaces and Names

Operations have meaningful names that describe what they do. A Sequence executes operations in sequence. A Branch chooses a path based on a condition. A Retry attempts an operation multiple times.

This explicitness extends to the parameters too. When you see:

```python
Retry(
    network_operation,
    max_attempts=5,
    backoff_factor=2.0,
    initial_delay=1.0
)
```

It's immediately clear what's happening - no magic, no mystery.

### Developer Experience: Intuitive APIs and Error Handling

We've all felt the pain of debugging complex asynchronous code. Loomi's operations are designed to make development and debugging less painful with:

- Intuitive APIs that follow Python norms
- Detailed error messages that tell you what went wrong and where
- Consistent error propagation
- Built-in observability and logging

## Executor Interface

### Accessing the Executor

Every Loomi app has an executor that provides access to operations and runs them. You can access it using either:

```python
# Full name
app.executor

# Short alias
app.ex
```

The executor is available as soon as your app is initialized, so you can use it to define operations:

```python
from loomi import AsyncApp

app = AsyncApp()

def define(self):
    return self.ex.Sequence(
        self.ex.Function(self.fetch_data),
        self.ex.Function(self.process_data)
    )
```

### ExecutorProtocol Overview

The executor provides two main things:

1. **Operation factories** - These are the classes you use to create operations:
   - `Function`, `App`
   - `Sequence`, `Parallel`, `Branch`, `Loop`
   - `Delay`, `Timeout`, `Retry`
   - `Map`, `Subscribe`

2. **Execution methods** - Methods that actually run your operations:
   - `execute()` - Runs an operation with an optional parent context
   - `exec_*()` - Methods for executing specific operation types

### Sync vs Async Executors

Loomi supports both synchronous and asynchronous execution:

- `AsyncExecutorProtocol` - For async applications using `async/await`
- `SyncExecutorProtocol` - For synchronous applications

The interfaces are nearly identical, with the main difference being that async methods have `async/await` markers. The operation factories and patterns are the same across both.

```python
# Async
await app.executor.execute(operation)

# Sync
app.executor.execute(operation)
```

### Custom Executor Adapters

Loomi only defines the interfaces for executors - you can plug in your own implementation. This means you can adapt Loomi to work with your existing systems or create specialized executors for specific use cases.

Want to run operations in a distributed manner across multiple machines? Create a distributed executor adapter. Need special monitoring or observability? Build it into your executor.

This adaptability is part of what makes Loomi powerful - the operations interface is consistent, but how those operations execute can be tailored to your needs.

## Operation Types

Loomi provides a rich set of built-in operations that cover most common application needs. These operations form the vocabulary for expressing your application's logic.

### Atomic Operations

Atomic operations are the basic building blocks that do actual work.

#### Function

The simplest operation - it executes a callable that performs some work:

```python
def update_user_data(context):
    user_id = context.scope.get("user_id")
    data = context.scope.get("user_data")
    # Do something with the data
    context.scope.set("user_data_updated", True)

# Create the operation
update_op = app.ex.Function(update_user_data)
```

Functions can be either sync or async depending on your executor type.

#### App

The App operation lets you execute another Loomi app as an operation. This is extremely powerful for building modular applications:

```python
user_service = UserServiceApp()
analytics_service = AnalyticsApp()

# Use these apps as operations
app.ex.Sequence(
    app.ex.App(user_service, state_path="user_service"),
    app.ex.App(analytics_service, state_path="analytics")
)
```

The `state_path` parameter lets you mount each app's state at a specific location in your parent app's state tree.

### Flow Control Operations

Flow control operations determine the execution path of your application based on conditions and structure.

#### Sequence

Executes operations one after another:

```python
app.ex.Sequence(
    app.ex.Function(fetch_data),
    app.ex.Function(transform_data),
    app.ex.Function(save_data)
)
```

Each operation completes before the next one starts. If any operation fails, the sequence stops (unless configured otherwise).

#### Parallel

Runs operations concurrently:

```python
app.ex.Parallel(
    app.ex.Function(fetch_user_data),
    app.ex.Function(fetch_product_data),
    app.ex.Function(fetch_recommendations),
    max_concurrency=2  # Run at most 2 operations simultaneously
)
```

You can control concurrency with `max_concurrency`:
- Set to 1 for sequential execution (same as Sequence)
- Set > 1 to limit concurrent operations
- Set to -1 or 0 for unlimited concurrency

#### Branch

Makes decisions based on conditions:

```python
app.ex.Branch(
    {
        "admin": app.ex.Function(admin_flow),
        "user": app.ex.Function(user_flow),
        "guest": app.ex.Function(guest_flow)
    },
    condition=lambda ctx: ctx.scope.get("user_role")
)
```

You can specify the condition as a function or path to state:

```python
# Using a state path
app.ex.Branch(
    {
        True: app.ex.Function(premium_content),
        False: app.ex.Function(free_content)
    },
    condition_path=("user", "is_premium")
)
```

#### Loop

Repeats an operation while a condition is true:

```python
app.ex.Loop(
    app.ex.Function(process_item),
    condition=lambda ctx: ctx.scope.get("items_left") > 0,
    max_iterations=100,  # Safety limit
    on_finish=app.ex.Function(finalize_processing)
)
```

The loop can use a condition function, a path to a boolean in state, or just a maximum number of iterations.

### Timing Operations

Timing operations help control when and how long operations execute.

#### Delay

Pauses execution for a specified duration:

```python
# Fixed 2-second delay
app.ex.Delay(2.0)

# Dynamic delay based on state
app.ex.Delay(delay_path=("config", "wait_time"))

# Function-based delay
app.ex.Delay(lambda ctx: ctx.scope.get("base_delay") * ctx.scope.get("multiplier"))
```

#### Timeout

Limits how long an operation can run:

```python
app.ex.Timeout(
    app.ex.Function(potentially_slow_operation),
    timeout=5.0,  # 5 second timeout
    on_timeout=app.ex.Function(handle_timeout)
)
```

If the operation doesn't complete within the timeout, it's cancelled and the optional `on_timeout` operation runs.

#### Retry

Attempts an operation multiple times with backoff:

```python
app.ex.Retry(
    app.ex.Function(network_request),
    max_attempts=5,
    backoff_factor=2.0,
    initial_delay=1.0,
    retry_on=[NetworkError, TimeoutError]
)
```

This is perfect for operations that might fail temporarily (like network requests) but should eventually succeed.

### Collection Operations

Collection operations work with multiple items.

#### Map

Applies an operation to each item in a collection:

```python
app.ex.Map(
    app.ex.Function(process_user),
    items_path=("users", "active"),
    max_concurrency=3  # Process up to 3 users at a time
)
```

The operation is executed for each item, with the item key and value accessible in the context.

### Reactive Operations

Reactive operations respond to changes in state.

#### Subscribe

Executes an operation when watched state changes:

```python
app.ex.Subscribe(
    app.ex.Function(update_ui),
    watch_path=("user", "preferences"),
    depth=1,  # Watch direct children too
    once=False  # Keep watching for changes
)
```

This is powerful for creating reactive applications that respond to state changes automatically.

## Higher Order Operations

Higher order operations are operations that create or return other operations. They're like operation factories that compose multiple primitive operations into reusable patterns.

### Concept and Purpose

The main benefits of higher order operations are:

1. **Reuse complex patterns** - Define a pattern once, use it everywhere
2. **Encapsulate logic** - Hide complexity behind a simple interface
3. **Create domain-specific operations** - Build operations that speak your application's language

### Built-in Example (ReactiveMap)

Loomi includes some higher order operations out of the box. One example is `ReactiveMap`:

```python
from loomi import ReactiveMap

# Process all existing users and any new ones that get added
app.ex.ReactiveMap(
    app.ex.Function(process_user),
    items_path=("users"),
    max_concurrency=2
)
```

`ReactiveMap` combines a `Map` operation (to process existing items) with a `Subscribe` operation (to process new items as they're added). It's much cleaner than writing this pattern yourself each time.

## Working with Operations

### Error Handling Patterns

Every operation accepts `error_behavior` and `on_fail` parameters:

```python
app.ex.Function(
    risky_operation,
    error_behavior="continue",  # Don't stop execution on error
    on_fail=app.ex.Function(handle_error)  # Run this if an error occurs
)
```

Error behaviors:
- `"fail"` (default) - Stop execution and propagate the error
- `"continue"` - Record the error but keep executing next operations

For more sophisticated error handling, combine operations:

```python
app.ex.Branch(
    {
        True: app.ex.Function(handle_success),
        False: app.ex.Function(handle_failure),
    },
    condition=lambda ctx: not ctx.scope.get("error", False)
)
```

### Operation Composition Patterns

Here are some common patterns for composing operations:

**Pipeline Pattern**:
```python
app.ex.Sequence(
    app.ex.Function(extract_data),
    app.ex.Function(transform_data),
    app.ex.Function(load_data)
)
```


**Conditional Execution Pattern**:
```python
app.ex.Sequence(
    app.ex.Function(validate_input),
    app.ex.Branch(
        {
            "valid": app.ex.Function(process_valid_input),
            "invalid": app.ex.Function(handle_invalid_input)
        },
        condition_path=("validation", "result")
    )
)
```

**Retry with Backoff Pattern**:
```python
app.ex.Retry(
    app.ex.Timeout(
        app.ex.Function(network_operation),
        timeout=3.0
    ),
    max_attempts=5,
    backoff_factor=2.0
)
```

### Practical Examples

**User Registration Flow**:
```python
def define(self):
    return self.ex.Sequence(
        self.ex.Function(self.validate_registration_data),
        self.ex.Branch({
            "valid": self.ex.Sequence(
                self.ex.Function(self.create_user),
                self.ex.Function(self.send_welcome_email),
                self.ex.Function(self.provision_resources)
            ),
            "invalid": self.ex.Function(self.return_validation_errors)
        }, condition_path=("validation", "status")),
        error_behavior="fail",
        on_fail=self.ex.Function(self.log_registration_error)
    )
```

**Data Processing Pipeline**:
```python
def define(self):
    return self.ex.Sequence(
        self.ex.Function(self.fetch_data_from_api),
        self.ex.Map(
            self.ex.Function(self.process_data_item),
            items_path=("data", "items"),
            max_concurrency=5
        ),
        self.ex.Function(self.aggregate_results),
        self.ex.Function(self.store_results)
    )
```

## Conclusion

Loomi's operations interface provides a powerful way to build applications from composable, state-bound pieces. By separating what your application does (the operations) from how it does it (the executor implementation), Loomi gives you flexibility without sacrificing clarity or consistency.

You can start simple with basic operations, then gradually compose them into more sophisticated flows as your application grows. The consistent interfaces and predictable behavior make it easy to reason about your code, even as complexity increases.
